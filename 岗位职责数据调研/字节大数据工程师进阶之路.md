## 第一部分：字节大数据高级工程师真正在做什么

### 1. 日常核心问题（按痛苦程度排序）

#### 第一层：数据 Pipeline 的"熵增"对抗

不是"写一个 Spark Job"这么简单。真正的日常是：
- 上游 30 个业务线的埋点格式**每天都在变**，你的 Pipeline 凌晨 3 点挂了，因为某个产品经理让前端多加了一个 JSON 字段，类型从 `string` 变成了 `struct`
- 你花了 40% 的时间不是在写新代码，而是在**防止老 Pipeline 腐化**——Schema 变更、数据漂移、小文件爆炸、分区倾斜
- 真正的核心问题是：**如何在 1000+ 个下游依赖方不知情的情况下，让数据仍然准时、准确地到达**

#### 第二层：实时与离线的"假边界"

字节的实际情况是：
- 不是"实时 vs 离线"二选一，而是 **Lambda 架构的反模式每天都在发生**——实时链路和离线链路算出来的同一个指标，对不上
- 你在 debug 的不是"延迟太大"，而是"实时链路修正了 3 天前的回刷数据，但下游已经用旧数据做了决策"
- **真正的痛点：Exactly-Once 语义在跨系统（Kafka → Flink → Hive → Redis）时根本不存在**，你要自己设计幂等和回溯机制

#### 第三层：数据治理是政治问题，不是技术问题

- 一个核心维度表有 14 个团队都说自己"拥有"它，但没有人真正维护
- 数据血缘追踪到了第 7 层，你发现源头是一个实习生 3 年前写的 Python 脚本，每天还在 crontab 上跑
- **真正的治理不是加 Catalog，是搞清楚"谁在用、谁能改、错了谁负责"**

### 2. 实际技术栈

#### 字节的真实技术选型逻辑

**能用自研的绝不用开源，但自研的核心思想 90% 来自开源**

| 层级 | 开源对标 | 字节自研/魔改 | 选型逻辑 |
|------|---------|-------------|---------|
| **存储** | HDFS / S3 | ByteStore（自研分布式存储） | HDFS 的小文件问题在小红书/抖音场景下是灾难，自研解决了元数据瓶颈 |
| **消息队列** | Kafka | BMQ（ByteMQ） | 万亿级/天的吞吐量，开源 Kafka 的 Controller 选举和 ISR 机制扛不住 |
| **实时计算** | Flink | 深度魔改 Flink + SQL 化平台 | Flink 内核保留，但 State Backend 自研，SQL 化让非工程师也能写实时任务 |
| **离线计算** | Spark / Hive | Spark 魔改 + 自研调度 | Spark 的 Dynamic Resource Allocation 在万级节点集群上有严重问题 |
| **OLAP** | ClickHouse / Doris | ByteHouse（基于 ClickHouse 魔改） | 自研了分布式元数据管理和物化视图 |
| **调度** | Airflow / DolphinScheduler | 自研 DAG 调度平台 | Airflow 的 Scheduler 单点瓶颈在万级 DAG 场景下无法接受 |
| **数据治理** | Atlas / DataHub | 自研 Data Catalog + 血缘平台 | 血缘数据量太大，开源方案根本跑不动 |

#### 技术栈演进趋势（2024-2026）

1. **Spark → Spark + Native Engine**：类似 Gluten/Velox 的 Native 执行引擎，把 Spark 的物理执行从 JVM 搬到 C++，TPC-DS 场景提升 2-3x
2. **Flink SQL 化 + AI 辅助调优**：让产品经理直接写 Flink SQL，AI Agent 自动优化 State TTL、Parallelism、Checkpoint 间隔
3. **存算分离是标配**：数据湖（Iceberg/Hudi）+ 自研存储底座，计算集群按需弹性伸缩
4. **实时数仓正在吃掉离线数仓的份额**：原来 T+1 的报表 70% 变成了分钟级

### 3. 最佳实践和方法论

#### 定位性能问题的思维框架（第一性原理）

```
不要直接看 Flame Graph。
先问三个问题：
1. 数据量真的需要这么多吗？（90% 的"性能问题"是读了太多不需要的数据）
2. Shuffle 真的需要吗？（你能用 Broadcast Join 吗？能提前聚合吗？）
3. 等价的串行操作，能不能用列存 + 向量化一次扫完？
```

**具体操作：**
- **看数据倾斜，别看平均延迟**——P99 才是你的用户感受到的，P50 是骗自己的
- **Spark 任务的第一个瓶颈永远是 Shuffle**，看 Spill to Disk 的量，不是看 Stage Duration
- **Flink 的第一个瓶颈是 State**——RocksDB 的 Compaction 风暴会让你的 Checkpoint 超时，不是你 Job 写的有问题

#### 设计可靠 Pipeline 的三个原则

1. **Idempotency First**：每个 Task 都必须可以重跑至少 10 次而不产生重复数据。实现方式：`output_path = f"{dt}_{attempt_id}"`，最后 Atomic Rename
2. **Fail Fast, Recover Faster**：凌晨 2 点挂掉可以接受，但凌晨 2:05 必须已经自动重试了。告警延迟 > 自动重试延迟才有意义
3. **Data Contract, Not Data Schema**：Schema 只是字段名和类型，Contract 还包含"非空率、枚举值范围、延迟 SLA"。用 Great Expectations 或自研框架做 Contract 校验

#### 监控的六层模型

```
L1: 任务是否在跑？（调度心跳）
L2: 任务是否跑完？（Success/Failure）
L3: 数据是否准时到达？（SLA 监控，比如"凌晨 5 点前产出"）
L4: 数据量是否合理？（同比/环比波动 > 30% 告警）
L5: 数据内容是否正确？（抽样校验 + 业务规则）
L6: 下游是否正常消费？（端到端延迟）
```

**大部分团队只做到了 L2，字节的要求是至少到 L4。**

### 4. AI 时代下这个岗位的演变

| 原来 | 现在 |
|------|------|
| 手写 Spark SQL，调试 30 分钟 | Copilot 生成，人工审核边界条件，5 分钟 |
| 数据质量问题靠人肉查 | Agent 自动巡检，发现波动自动归因到上游变更 |
| 新人 oncall 看不懂告警 | Agent 先做根因分析，给到人时已经是"疑似上游 Kafka topic 分区数变更导致 Lag 上涨" |
| 写文档靠自觉 | AI 从代码 + 血缘自动生成数据字典和 Pipeline 文档 |

#### 未来 3 年核心竞争力

1. **从"会写 Spark"变成"会设计 Data System"**——代码生成被 AI 吃掉，但系统设计（一致性、可用性、成本优化）是人的判断
2. **AI 调优师**——不是手调参数，而是设计**让 AI 自动调参的 Reward Function**，理解业务目标比理解 GC 日志更重要
3. **Data Product 思维**——不再交付"一张表"，而是交付"一个带 SLA、带 Contract、带血缘的 Data Product"
4. **多模态数据处理**——日志/视频/图片/Embedding 统一处理 Pipeline，不再是纯结构化数据的世界

> **核心认知：字节大数据高级工程师的真正壁垒不是"会用 Flink/Spark"，而是在 1000 个上下游团队、每天 PB 级数据、凌晨 SLA 压身的真实约束下，依然能设计出"挂了能自愈、慢了能自优化、错了能自回溯"的数据系统。**

## 第二部分：3 年进阶路线——核心指导思想、具体执行与自测标准

### 一、核心指导思想（The Why）

#### 原则 1：向"问题本质"对齐，而非"工具热度"对齐

**❌ 错误姿势：** "今年 Flink 很火，我要学 Flink；明年 Rust 很火，我要学 Rust。"

**✅ 正确姿势：** "我面对的核心问题是**大规模数据在分布式环境下的可靠传输与计算**。Flink 是解决这个问题的当前最佳工具之一，我学的是它背后的**流式计算语义、状态管理、Checkpoint 机制、Exactly-Once 保证**——这些概念 10 年后依然存在，只是换了实现。"

**3 年不变的本质问题清单：**

| 本质问题 | 今天的实现 | 3 年后的实现（推测） |
|----------|-----------|-------------------|
| 数据如何可靠传输？ | Kafka / BMQ | 存算分离的流存储 + 内置 AI 路由 |
| 数据如何高效计算？ | Spark / Flink | Native Engine + AI 优化器 |
| 数据如何被找到和理解？ | Data Catalog | AI Agent 驱动的语义搜索 |
| 数据质量如何保证？ | 人工规则 + 监控 | Agent 自动巡检 + 自动修复 |
| 如何用数据驱动决策？ | 报表 / 看板 | 自然语言 → SQL → 可视化全自动 |

**行动准则：每学一个工具，写一句话说明它解决了哪个本质问题，以及它的实现原理。如果写不出来，你就在"用工具"而不是"理解问题"。**

---

#### 原则 2：向"可验证的落地价值"对齐，而非"技术深度"对齐

**❌ 错误姿势：** "我今年用 Rust 重写了公司的 ETL 链路，性能提升了 30%。"

**✅ 正确姿势：** "我把核心报表的 SLA 从 T+1 上午 10 点提前到了凌晨 5 点，业务方晨会可以直接用。这是通过优化上游数据就绪时间和增量计算实现的，没有换技术栈。**可验证的价值：每天为 200 个运营和产品节省 5 小时等待时间。**"

**价值换算公式（每次做完一件事就填）：**

```
我做的事：__________________
影响的对象：____ 人
每个人节省/获得：____ 小时/元/决策质量
年化价值 = 人数 × 单位价值 × 频率
```

**如果你算不出这个公式，这个事就不值得做。**

---

#### 原则 3：向"AI 放大器"对齐，而非"AI 替代品"对齐

**AI 放大器思维模型：**

```
你的价值 = 你的判断力 × AI 的执行力

AI 的执行力正在以 10x/年 增长
但你的判断力如果为 0，乘什么都还是 0
```

**什么不会被 AI 吃掉（3 年窗口内的安全区）：**

| 会被吃掉 | 不会被吃掉 |
|----------|-----------|
| 写 Spark/Flink 代码 | 决定"这个指标不该用实时算，因为业务含义需要 T+1 才能稳定" |
| 调 parallelism 参数 | 定义 SLA 的分级标准：什么是 P0（影响收入），什么是 P3（nice to have） |
| 生成数据血缘图谱 | 判断"这个数据源的信任度有多高，能否直接给 CEO 用" |
| 写监控 SQL | 设计"当监控告警触发时，先自动重试还是先通知人"的决策树 |

> **核心认知：AI 会吃掉"怎么做"，但"做什么、为什么做、做到什么程度算好"是人的领地。**

### 二、3 年路线图（分阶段执行）

#### 第一阶段：0-12 个月 —— "成为数据的全能医生"

**目标：** 能独立诊断和修复一个数据系统的任何常见故障，并且每次修复后系统比之前更健康。

**学什么（按优先级排序）：**

1. **分布式系统的"不可能三角"**
   - 资源：《Designing Data-Intensive Applications》全书（不要跳章，每一章都对应一种你会遇到的故障模式）
   - 检验：给一个非技术同事讲清楚"为什么 Spark Join 两个大表会 OOM，以及 4 种解决方案的 tradeoff"

2. **一个计算引擎的源码级理解**
   - Spark 或 Flink，不是会用 API，是能解释：一个 SQL 从你提交到结果输出，经过了哪些阶段？
   - Shuffle 的 3 种实现（Hash / Sort / Broadcast）各自在什么条件下触发？
   - 为什么你加了 `repartition(200)` 反而更慢了？

3. **数据建模的"物理现实"**
   - 学：Z-order、Data Skipping、Bloom Filter Index、物化视图的刷新策略
   - 核心认知：**数据建模不是在画 ER 图，是在安排磁盘上字节的物理排列以最小化查询时的 IO**

**做什么（必须有 GitHub 可验证的产出）：**

```
一个开源项目：用 Docker Compose 搭建一个"迷你快手/抖音数据平台"
包含：
- Kafka/Flink SQL 做实时数仓
- Spark/Iceberg 做离线数仓
- 自建监控 + 告警
- 故意注入故障（延迟、丢数据、倾斜）并自动恢复
- 写一篇 5000 字博客解释每个设计决策

这不是玩具项目。这是你向任何面试官证明"我不是会用工具，我理解系统"的证据。
```

**自测标准（每季度自检，必须诚实回答）：**

- [ ] 给我一个慢查询，我能在 10 分钟内定位到是 IO 瓶颈、CPU 瓶颈、还是数据倾斜
- [ ] 给我一个 Pipeline 故障，我能在 5 分钟内判断是上游数据问题、代码 Bug、还是资源不足
- [ ] 我能不看文档，画出 Spark Job 从提交到 Shuffle 到落盘的完整时序图
- [ ] 我今年读了至少 3 个开源组件的源码（不是看博客，是看源码），并写了注释

---

#### 第二阶段：12-24 个月 —— "从 Builder 到 Architect"

**目标：** 不再只是"开发一个任务"，而是"设计一个系统"。能在 3 个以上团队/50 个以上下游依赖的约束下，做出正确的架构决策。

**学什么：**

1. **系统设计的方法论**
   - 每遇到一个设计决策，写出：约束 → 选项 → Tradeoff → 决策 → 验证方法
   - 关键认知：**没有正确的架构，只有在当前约束下代价最小的架构**

2. **数据治理的"政治学"**
   - Data Mesh vs Data Fabric vs Centralized Data Platform
   - 学：如何定义 Data Product 的 Ownership？如何设计 SLA 的升级路径？如何度量数据 ROI？
   - 资源：《The Data Warehouse Toolkit》（Kimball）+ DataHub/Apache Atlas 实际部署文档

3. **AI 工程化**（领先的关键差异化能力）
   - 如何用 LLM 做数据质量自动巡检？
   - 如何用 RAG 做数据文档自动生成？
   - 如何用 Agent 做 Pipeline 自动修复？

**做什么（必须有业务影响的产出）：**

```
在公司落地一个"AI + 数据"的项目，必须有可量化的结果：

选项 A：AI 辅助 SQL 优化
- 输入：过去 3 个月所有的慢查询日志
- 输出：一个 Agent 能自动分析慢查询原因并建议优化方案
- 指标：优化建议的采纳率 > 60%，被采纳的查询平均提速 > 50%

选项 B：数据质量 AI 巡检
- 输入：核心表的昨天数据
- 输出：一个 Agent 能自动判断"今天的数据是否异常"，准确率 > 85%
- 指标：比人工巡检早发现异常 > 2 小时

选一个，3 个月内落地，拿到数字，写进简历。
```

**自测标准：**

- [ ] 我的 Slack/飞书 里至少有 3 个非技术同事主动找我问数据问题
- [ ] 我能给 CTO 讲清楚"为什么我们要从 Hive 迁到 Iceberg，迁移成本和收益分别是多少"
- [ ] 我有一个 AI + 数据的落地项目，并且有可量化的业务指标
- [ ] 我能在 30 分钟内设计一个日增 10TB 的实时数仓架构，并解释每个组件的选型理由

#### 第三阶段：24-36 个月 —— "价值定义者"

**目标：** 不只是在解决别人定义的问题，而是在**定义什么问题是值得解决的**。

**学什么：**

1. **业务的财务模型**
   - 核心认知：如果你的数据明天消失，业务的哪个指标会跌？跌多少？如果你答不上来，你就还没有不可替代的价值。

2. **AI Native 数据架构**
   - Embedding 作为一等数据类型，和 VARCHAR/INT 平级
   - 向量索引和 B-Tree 索引在同一个查询计划中共存
   - 数据血缘追踪从"表级别"变成"语义级别"

3. **组织影响力**
   - 学会写 RFC / Design Doc，让一个房间里最资深的人说"我同意你的方案"
   - 学会做 Technical Talk，让 50 个人听完知道"这个方向是对的"

**做什么：**

```
选项 A：主导一个数据基础设施的迁移/升级
选项 B：定义并落地一套数据 SLA 体系
选项 C：开源一个有影响力的项目（目标：GitHub 500+ Stars）
```

**自测标准：**

- [ ] 有一个非我司的人因为我的工作而改变了技术选型
- [ ] 我能给 CEO 讲清楚"我们在数据上的投入产出比是多少"
- [ ] 如果我明天离职，我留下的文档和系统能让接班人在 2 周内上手
- [ ] 我有至少一个 AI + 数据的项目在简历上，面试时能讲 30 分钟不重样

### 三、日常执行纪律

#### 每周时间分配的"正确"比例

| 活动 | 错误比例 | 正确比例 | 说明 |
|------|---------|---------|------|
| 写业务代码 | 80% | 40% | 不能超过一半。如果超过，你在成为"数据码农" |
| 读源码/论文/技术博客 | 5% | 20% | 每周至少 1 天纯学习。3 年就是 150 天，这是你和别人的差距 |
| 写文档/博客/总结 | 0% | 15% | **写作是思考的加速器**。不写 = 没真正理解 |
| 做 AI + 数据的实验 | 0% | 15% | 每周半天，试一个新 Agent/新工具/新思路 |
| 和业务方聊天/了解问题 | 5% | 10% | 最好的技术方案来自对问题本质的理解 |

#### 每日的"最小正确行动"

```
每天早上 30 分钟：读一篇技术博客或论文的一个章节（不是刷 Twitter/知乎）
每天下午 30 分钟：写工作日志（今天做了什么事？为什么这样做？有没有更好的方式？）
每周五下午 2 小时：本周学习总结 + 一篇博客草稿
每月最后一个周末：自测本月的 Checklist，诚实打分，调整下个月计划
```
