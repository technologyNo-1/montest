# 第一部分 · 第一性原理:Agent 系统的最小本质

## 1.1 一页说清 Agent 是什么

去掉所有框架名词,Agent 系统的本质是四个环节构成的**自动闭环**:

```
感知(拿到上下文/状态) → 决策(模型推理) → 行动(调用工具/产生输出) → 反馈(校验结果)
        ↑                                                        ↓
        └──────────────── 循环(根据反馈更新状态,再决策) ←────────┘
```

传统程序 = **写死的流程**(if/else + 函数调用栈,谁走哪一步是编译期决定的)。
Agent 程序 = **运行时才决定流程**(每一步"该做什么"由大模型根据当时的上下文决定)。
**这是两者唯一、也是最深刻的差异:控制权从"写代码的人"转移到了"运行时的大模型"。**

工程上代价与收益都源于此:
- 收益:能处理没预写过的分支,泛化到新场景。
- 代价:模型会出错、会胡来、会绕圈,你必须用工程手段把"运行时决策的不确定性"约束住。

## 1.2 从闭环反推:为什么 Python 能力是这条链的"地基"

| 闭环环节 | 工程落地 | 需要的 Python 能力 | 优先级 |
|---|---|---|---|
| 感知/状态 | 上下文、Graph State、checkpointer 持久化 | 类型系统(TypedDict/Pydantic)+ 序列化 | **L0** |
| 决策 | LLM 调用(并发、流式、结构化输出) | asyncio + Pydantic 输出约束 | **L0** |
| 行动 | 工具(schema 化)、重试、并行 | Pydantic 工具契约 + 异常/上下文管理 + asyncio 并发 | L0/L1 |
| 反馈循环 | 图设计、循环控制、eval、观测 | 一等函数/图抽象 + 可观测性 + 测试 | L1 |

结论一句话:**agent 开发不是"会调 LangChain API",而是"用类型系统管状态、用 asyncio 管 IO、用函数组合管控制流、用异常管理不确定性"。**

## 1.3 三个必须先想通的反直觉点

1. **LLM 输出是"概率字符串",你却让它决定程序控制流** —— 所以一切结构(工具参数、状态、路由)都必须有**强类型契约**拦截,而不是靠它自觉遵守。Pydantic 不是装饰,是护栏。
2. **Agent 是 I/O 密集,不是计算密集** —— 瓶颈永远在"等待网络/模型返回",所以**异步是默认选项,不是优化项**。同步写 agent = 单请求串行 = 把 GPU 和钱包都浪费在排队上。
3. **状态是你的记忆,持久化是它的保险** —— 对话记忆、checkpoint、断点续跑全靠"状态可序列化、可重建"。不会序列化 = agent 一断就失忆。

# 第二部分 · 苏格拉底式提问:先想通,再动手

> 这 8 个问题先自己写一版回答,再看"要点"。想通它们,你对 agent 的理解会超过 90% 只背 API 的人。

## S1. 如果 LLM 每次都可能输出非法 JSON,你为什么还敢把它的输出当控制流?
- **要点**:输出约束(Pydantic + 工具 schema)把"自由文本"降维成"合法结构";非法结构走重试/降级,而不是直接进逻辑。控制流的合法性由**契约**保证,不由**运气**保证。

## S2. LangGraph 用"图",传统编程用"函数调用栈"——两者在"状态"上有什么本质差异?
- **要点**:图把状态**显式化、外置化**(State + checkpointer),所以天然支持:中断续跑、并行、人机协作(HITL)、跨调用持久化。**图是"状态显式化"的载体。**

## S3. 为什么非得是 Python 不可?C++/Go/TS 不也能写 agent 吗?
- **要点**:Python 赢在**成本门槛低 + 生态全覆盖 + 上手快**;它的性能劣势在 agent 的 I/O 密集场景下不构成瓶颈。瓶颈在哪,选型就往哪配。

## S4. 如果只有 1 个用户、1 个请求,异步还有必要吗?
- **要点**:异步 = 让 CPU 在等待时去干别的活(并发) + 让数据边到边推(流式)。agent 必然多样 IO、必然流式,所以必学。

## S5. token 是钱、是时间、是上下文窗口——工程上所有"省一点"都是在跟什么做交换?
- **要点**:agent 工程 = **用 token 换确定性**的权衡艺术。省 token 之前先问:我省掉的是不是"决定成败的上下文"?该花的钱花在护栏(校验/重试/观测)上。

## S6. 状态是 agent 的命门——checkpointer 存的是什么?它和你程序里的全局变量有什么不同?
- **要点**:可持久化、可重建、可断点续跑——这是 agent 能"越跑越有记忆"的前提。全局变量不可恢复、并发共享就乱、跑完就丢。

## S7. 什么时候**不该**用 agent?
- **要点**:全确定性流程、延迟敏感、成本极敏感、结果必须可审计——这些场景用 if/else、查表、传统状态机更便宜可靠。**知道"何时不用"才是架构师的标志。**

## S8. 测试一个依赖 LLM 的系统,本质困难在哪?你如何把不确定性变成可测的?
- **要点**:把系统切成"确定逻辑(可单测)+ 模型边界(可 mock)+ 行为质量(需 eval)"三层。不会分层 = 一切测试都 flaky。

# 第四部分 · 优先级排序:L0–L3

> 判断标准:**你对"自动闭环"的哪个环节没有它就会崩。**

## 🟥 L0 · 决定性(学不会寸步难行)
- **类型系统 + 类型注解**:TypedDict、Optional/Union/Literal、dataclass → 状态契约(→ day01)
- **Pydantic v2**:validate/dump、Field、validator、嵌套、extra → 状态+工具契约(→ day01/02)
- **asyncio**:async/await、事件循环、gather/Task、超时/取消、async for → 决策/行动 IO(→ day03)

## 🟧 L1 · 主力(决定质量与体验)
- **一等函数/闭包/装饰器**:partial、@tool/@node 原理、手写 retry+backoff+jitter(→ day04)
- **生成器/async 生成器**:yield、async for、惰性、流式透传(→ day04)
- **异常 + 上下文管理**:错误分类、finally、with、自定义异常(→ day05)
- **数据容器操作**:dict 合并、setdefault、deque、深浅拷贝(→ day02)

## 🟨 L2 · 工程化(决定能否落地)
- **序列化/配置**:pydantic dump、json 往返、.env、checkpointer 可重建(→ day05)
- **模块与依赖**:uv 工程、包结构、__name__ 惯用法(→ day05)
- **可观测性**:logging、trace、token/延迟埋点(→ 贯穿)
- **基本测试**:单测节点、mock 模型边界(→ day07)

## 🟩 L3 · 够用即可(把时间让给 L0/L1)
面向对象深入、多进程/多线程、元类/GC 炫技、数据库(SQL)——用到再学。

# 第六部分 · 行业趋势与未来(2026 时点,决定你押哪)

> 这些趋势不是让你现在学工具,而是告诉你"练好的底层能力会被哪个方向吃掉"。

1. **durable execution 成为新常态**:LangGraph/Gemini 都在强调"状态持久化 + 断点续跑 + 人机协作(HITL)"。→ 你的投资回报:**序列化、状态设计、中断恢复**(day05/06)正是这块的地基。
2. **工具是 agent 的四肢,协议在标准化**:MCP(Model Context Protocol)、ACP(Agent Client Protocol)正在把"工具/agent 即服务"标准化。→ 你的回报:**Pydantic 工具契约 + 参数校验**是任何协议都绕不过的公共底座(day01/02)。
3. **多 agent 协作是下一个主战场,但"贵且难协调"**:teams/多会话、任务委托、消息协议解决"协调";成本与协调失败是拦路虎。→ 你的回报:**图设计 + 循环终止 + 错误分类**(day06/05)决定你能不能写出不乱转圈的多 agent。
4. **eval 驱动开发**:没有评测集,agent 改进就是玄学。数据/评测/回归成为一等公民。→ 你的回报:**把"模型边界"和"确定逻辑"分层的测试观**(S8/day07)是可迁移的架构能力。
5. **成本与延迟永远是真约束**:token 计价、缓存、小模型分流、流式优先。→ 你的回报:**异步 + 流式 + 并发控制**(day03/04)直接决定单位成本能换多少吞吐。
6. **一句话结论**:未来十年 agent 工程的地基是**状态、契约、并发、容错、评测**这五个词——恰好就是这 7 天的全部内容。学完它们,框架怎么换代你都不慌。

# 第七部分 · 结项标准:毕业=能独立交付一个 agent

## 7.1 结项项目(落在 `day07_capstone/`)

**做一个"离线可跑的检索式客服 agent"**:输入用户问题 → 从本地文档切片中检索 → 让"模型节点"回答(离线用确定性函数模拟)→ 工具可被调用/可重试 → 状态可持久化断点续跑 → 有人机协作挂起点。要求:

1. 用 Pydantic 定义工具参数(查库存/查价格),非法输入被拦截。
2. 用 asyncio 并发检索 2 个"数据源"(离线用 sleep 模拟)。
3. 用自定义异常区分"可重试/不可重试",网络类错误指数退避重试。
4. 用图(State + Node + 条件边)组织流程,循环必须有终止条件。
5. checkpointer 存状态,同 thread 断点可续跑。
6. 附 3 条 eval 断言(离线 mock 下稳定通过)。
