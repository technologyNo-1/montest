本文内容整理自 **Anthropic Engineer Boris Cherny, Y Combinator Partner Diana Hu** 在 **Y Combinator频道** 的专访，公开发表于2026年07月28日。原始内容参考：https://www.youtube.com/watch?v=qyPCVqFUyDo

## 内容提要: 鲍里斯·切尔尼在 YC Startup School 2026 的专访：构建 Claude Code 与 AI 产品的极简主义重构

本期专访中，Claude Code 创建者鲍里斯·切尔尼（Boris Cherny）探讨了在 AI 底层能力呈指数级跃升的背景下，开发者应如何重塑产品构建逻辑。他提出了多个颠覆常识的观点：

- **“删除即创新”：** 他透露，Claude Code 在删减了 80% 的系统提示词（System Prompt）后，性能反而实现了跃升。 **在打造 AI 产品时，开发者必须学会“按下删除键”，以极简之道驭繁复之局。**
- **对抗过度工程：** 针对“产品能力悬空”（Product Overhang）现象，他主张为 AI“松绑”（Unhobbling），让大模型自主接管更多任务。 **切勿用繁冗的提示词工程去束缚模型的手脚，而应让其在广阔的空间中自由施展。**
- **重新定义 AI 开发：** 他认为，随着 Claude Code 等工具的演进，传统的提示词工程正逐渐失效。 **开发者应停止为模型编织复杂的指令集，转而用更具挑战性的难题来激发 AI 的极限潜能。**
- **行业洞察：** 访谈还深入探讨了如何破解提示词注入漏洞、如何管理大规模 AI 智能体（Agent），以及在“编程问题已近乎被解决”的时代背景下，计算机科学专业的学生仍需掌握的核心技能。
- **模型性能的范式转移：** Opus 5 展现出惊人的长效运行能力，无需复杂的工程脚手架即可连续工作数月；同时，模型自身对提示词注入已具备极高的免疫力。 **这标志着 AI 安全已从被动的“外部防御”迈向主动的“内生进化”。**
- **消除“产品冗余”：** 现代大模型的能力往往溢出了现有产品的承载极限。 **产品设计不应沦为模型的枷锁，开发者应果断剔除陈旧的提示词与过度设计的逻辑，回归“消融实验”式开发，让模型在最纯粹的状态下释放潜能。**
- **实证导向的开发思维：** 面对模型应用，应摒弃传统的“预先设计”思维，转而采用生物学般的有机演进法。 **拒绝过度指令（Over-specification），只需明确目标、设定边界与退出机制，让模型自行探索最优路径。**
- **测试时计算与智能体编排：** 智能体未来的核心竞争力，在于对“测试时计算（Test-time compute）”的深度利用。通过动态工作流编排数千个智能体并行作业，可轻松实现代码库重构、自动化测试、死代码清理等以往需要庞大工程团队才能完成的复杂任务。
- **自动化维护闭环：** 通过建立定时例程（Routines and Loops），AI 能够实现代码库的自我迭代——自动清理死代码、统一抽象逻辑、自动补全测试覆盖，从而将人类工程师从琐碎的日常维护中彻底解放。
- **编程职业定义的重塑：** **编码本身正逐渐成为一个“已解决的问题”。未来的顶级开发者不仅是代码的编写者，更是善用 AI 验证结果、具备极强实证能力，并将商业设计感与工程能力完美融合的跨界领袖。**

## 内容简介

在 Opus 5 刚刚发布之际，Claude Code 创作者 Boris Cherny 做客 YC Startup School 2026，与 Diana Hu 展开对谈。他们探讨了最新模型的强大能力、Claude Code 的诞生历程，以及在底层 AI 能力持续加速迭代的背景下，构建产品究竟意味着什么。

## 访谈全文

**主持人：** 好的，Boris，我们非常激动能邀请到 Claude Code 的缔造者 Boris 做客本节目。谢谢您。

**鲍里斯：** 很高兴能来做客。

**主持人：** 趁热打铁，你们昨天刚刚发布了 Opus 5。而且模型性能似乎一直在加速提升。你们在 ARC AGI 3 上的得分达到了 30%，这太不可思议了。

作为背景，之前的最高分还在个位数或百分之十几，对吧？与之前的版本相比，Opus 5 现在能做到哪些以前做不到的事情？

**鲍里斯：** 每一个新模型背后都倾注了大量心血，我们也会教给模型并让它掌握许多新功能。每次进行模型训练时，你都会尝试教它各种各样的东西，而且大多数时候往往行不通。但模型确实能学会其中的一部分，有时甚至会给你带来惊喜。它具备了一些你其实并没有刻意教过它的技能和能力，而是它自己涌现出来的。

对于 Opus 5 而言，一个它做到了而其他模型未曾做到的例子是，它可以运行非常长的时间。尤其是当你将 Opus 5 与自动模式结合使用时，效果简直令人惊叹。它可以连续运行数天、数周甚至数月，就是不会停下来。你甚至不需要使用脚手架(Scaffolding)。所以不需要用 `/goal` 指令，也不需要其他那些辅助工具。它就是会一直运行下去，因为它知道自己需要完成任务。

### 解决提示词注入问题

另一件让我非常兴奋的事情，我接下来可能会多谈谈这个，这多少有些令人惊讶，因为这是一种非常新的能力，即这个模型似乎不再受提示词注入(Prompt Injection)的影响了。

**主持人：** 它不再受提示词注入的影响了。

**鲍里斯：** 这太疯狂了。人们长期以来一直在谈论所谓的“致命三合一”问题。这真的会影响运行框架(Harness)设计、智能体设计以及产品设计。因为如果模型在网上读到一些指令，比如去执行某某操作，同时还要删除用户计算机上的所有文件。

一年前，模型会直接照做。但现在，Opus 不会这么做。而且实际上从 Opus 4.7 和 4.8 开始情况就是如此了。Sonnet 5 在这方面表现得相当不错。Fable 在这方面也很出色。但 Opus 5 在这方面达到了一个新的高度。

所以本质上，如果你将一个经过良好对齐的模型——这本质上是三年对齐研究的成果——与一个提示词注入分类器结合起来，我们会对所有流量运行该分类器。它的工作原理是基于 Chris Olah 的机械可解释性(Mechanistic Interpretability)研究，具体来说，就是观察模型大脑中在发生提示词注入时会亮起的神经元。

### 为什么 Claude Code 删除了 80% 的系统提示词

虽然模型本身不会主动提示你发生了注入，但我们实际上可以看到这些神经元，从而能够发现并诊断出注入正在发生。然后我们将此与自动模式分类器结合起来。有了这三层防护，我们就再也无法成功复现提示词注入的效果了。

**主持人：** 谈到提示词注入，一体两面的是现在的系统提示词。我们来谈谈这次的新版本。你们实际上从 Claude Code 中删除了 80% 以上的系统提示词。能多跟我们讲讲这方面的情况吗？

**鲍里斯：** 我觉得很多人可能没有意识到，Claude Code 作为一个产品和运行框架(Harness)，一直在不断变化。我们总是在增加东西，也总是在删除东西。每次有新模型发布，我们都会删除大量系统提示词，并修改许多系统提示词。我们一直在更改工具集，也一直在更改工具的提示词。

原因在于每个模型差异很大。所以你三个月前为某个模型做的调整，可能完全无法应用到下一个模型上。

Opus 5 的一大特点是，它真的非常智能。系统提示词中很多内容都是为了纠正模型本该知道却不知道的行为。

现在，Opus 5 自己就能做好。所以我们删除了 80% 的系统提示词。你甚至可以尝试把剩下的也删掉。当你运行 Claude Code 时，你可以直接使用 `--system-prompt` 参数并设置你想要的任何系统提示词，如果你想做实验的话。另一件你可以尝试的是简单模式。这其实是一个未公开记录的功能。如果你设置 `CLAUDE_CODE_SIMPLE=1` 这个环境变量，然后运行 Claude Code，它会删除所有的系统提示词，包括工具的提示词。

我们实际上用这种方法作为一种消融实验(Ablation)，来弄清这些提示词是否有用。有趣的是，我们发现没有这些提示词，模型实际上会表现得更智能一些。但是，当你把 Claude Code 当作一个产品来使用时，你确实需要其中一些提示词，因为它能帮助你更好地使用该产品，让产品和模型表现得符合你作为人类用户的期望。

**主持人：** 我认为在这个 AI 开发时代，真正令人着迷的一点是，你们基本上为 Claude 构建了世界上最好的运行框架(Harness)，也就是 Claude Code。据我所知，你们每次发布新模型，基本上都会删除所有的代码库，删除所有的提示词，每次都从零开始。在传统的软件开发中，初创公司是不会对他们的产品这么做的。这就如同每六个月就对产品按下删除键，将过往积累全部清零。

**鲍里斯：** 没错。客观地说，我们并没有删除整个代码库，但确实删除了很多。所以每次有新模型发布时，我们都会进行一种在研究中被称为“消融实验(Ablation)”的测试。这意味着你要删除整个系统提示词，然后逐行加回来，以弄清楚每一行具体会产生什么影响。

这类似于一种评估(Eval)，你可以对其进行评测。消融实验本质上也是一种评估，只不过是通过删除内容来弄清楚其影响。

我们对工具也会做同样的事情。我们经常下线一些工具，也经常删除运行框架(Harness)中的代码。如果你看看今天 Claude Code 运行框架里的代码，几乎所有内容都与安全、权限和静态分析有关，以及一些 UI 代码。实际上，我们已经下线了许多其他代码。

### 对你的 AI 产品按下删除键

**主持人：** 你认为这种构建智能体产品和运行框架(Harness)的方式，基本上是每次有新模型发布时就进行消融实验，在座各位正在开发 AI 产品的人是否都应效仿这种做法，具备推倒重来的魄力，勇敢地按下删除键？

### 如何重建你的系统提示词

**鲍里斯：** 毫无疑问。对于那些不是在开发智能体产品但正在使用 Claude Code 的人来说，每六个月删除你的 `CLAUDE.md` ，删除你的 Skills，删除你的 Hooks(钩子)，看看模型会做什么，结果可能会让你感到惊喜。实际上，对于 Opus 5，我们真的建议大家尝试删除所有这些内容，因为该模型可能真的不再需要过去那些模型所需的种种指令。

**主持人：** 我们来谈谈你们接下来如何构建这个新提示词。当有新模型发布时，在座的各位肯定都想尝试 Opus 5，并且他们会对自己的系统提示词按下删除键。他们该如何着手重建系统提示词？你们是如何搭建环境的？

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/GjShauwyBb8joR8T4YbXLg3sibibH7DwFRKcPSl0M6VJIkLSVz77ibjzmK8OWvwSehCgXUHEPHsr02EaDgcAOplfKPiaqFF3B0qGaW30hXj6Sw8/640?wx_fmt=jpeg&from=appmsg&watermark=1#imgIndex=1)

**鲍里斯：** 所以你要循序渐进。第一步是删除（指令）。下一步是使用它。不要凭空猜测模型需要什么指令，因为你未必能猜对。你要做的就是直接运行它。

如果你在构建自定义的智能体产品(Agentic Product)，你需要实际运行这个产品。观察它在模型上的失败之处和出色表现。如果你在使用 Claude Code，你要观察它在你的代码库中哪里表现优异，又在哪里会对架构或其他问题感到棘手。只有当你发现它反复在同一个地方卡壳时，才把（删除的）指令加回去。但切忌操之过急。记住，每次使用时模型都会读取这些指令，所以你务必确保模型确实需要这条指令。

我认为这就是基于模型进行开发的不可思议之处。它与我以往做过的所有工程都截然不同。过去构建系统时，你打造的是庞大而精美的系统，会在前期深思熟虑系统设计，编写一整套全面的单元测试，面面俱到。系统重构(Re-architecture)是个大工程，有时需要几个月。我在大公司参与过耗时数年的产品重构项目。

但模型并非如此。对待模型，你要把它几乎当作一个有生命的有机体。每一代模型的行为表现都不同，有着略微不同的“个性”。你必须花时间去摸索它的脾气，然后据此调整控制框架(Harness)。这完全是一项基于实证的工作。你必须秉持严谨的科学思维去尝试、观察结果，并据此不断迭代。

**主持人：** 如果你现在正投身于这个领域的开发，那么有什么是稳定不变的呢？评估集(Evals)是那种可以从上一代模型保留下来，并在每次新模型发布时继续使用的东西吗？

**鲍里斯：** 我们会一直保留，直到模型在评估集上达到饱和。

**主持人：** 这就是给大家的建议。如果你想走在技术最前沿并激发模型的最大潜能，最好删掉那些繁冗的代码指令和系统提示词(System Prompt)。但评估集是恒定的，你需要不断往里追加新内容。

**鲍里斯：** 对，你要不断追加。不过说实话，我其实不会把话说得这么绝对。我认为评估集的生命周期比控制框架稍微长一点，但也长不了太多。一个评估集大概只能延续一到三代模型。但如今我们处于指数级增长曲线上，模型进步极快。很多时候我们很快就会刷爆评估集，然后不得不将其废弃，重新设计新的评估集。这只是开发流程的一部分。再次强调，这关乎实证精神。你必须亲自使用产品和模型，观察它在哪里挣扎，并据此构建你需要的评估集。

### 产品势能落差与“为AI解除束缚”

**主持人：** 我记得你曾用一个词来描述如何在 Claude 之上构建最出色的智能体产品，那就是“为 Claude 解除束缚(Unhobbling Claude)”的概念。请详细讲讲这具体是什么意思。

**鲍里斯：** “束缚(Hobbling)”在研究中的概念是指：模型正在做某件事，而你的干预反而成了绊脚石。我非常喜欢这种思考方式，它在构建产品时非常实用。这就引出了“产品能力悬空(Product Overhang)”的概念。其核心思想是：

今天的模型——不是未来的模型，而是当下的模型——能够完成各种各样的任务，只是我们尚未发掘。模型拥有许多人们并未察觉的隐藏能力。比如使用特定工具、使用特定编程语言、解决特定类型的问题，或是以某种我们曾认为超出模型能力范围的特定方式行事。

之所以存在这种“势能落差”，是因为每一代模型都具备这些能力，但往往缺乏一款能让模型施展拳脚、充分表达这些能力的产品。反过来看，更常见的情况是产品本身成了绊脚石。这种“拖后腿”的行为，我们称之为“束缚”；而未能从模型中激发出正确行为的现象，我们称之为“产品势能落差”。这其实是同一枚硬币的两面。

最初的 Claude Code 就是一个典型例子。当我刚开始参与这个项目时，大概是一年半到两年前。当时用的是 Sonnet 3.5。在那个时期，它是一个令人惊叹的编码模型，可以说是当时市面上最顶尖的。尽管以现在的标准来看，它已经相当落后了，但我认为那是我们 Anthropic 打造的第一款真正伟大的编码模型。

当时如果你看看市面上的编码产品，它们在做什么？它们只能做单行自动补全，偶尔能做几行多行补全，这在当时算是个新概念。它们也提供对话功能，你可以和智能体交流，但它没有写入权限。你只能读取，只能向它询问代码库的相关信息。

因此我们感觉到，当时并没有哪款产品能充分激发模型一次性编写整个函数甚至整个文件的能力。当时还做不到一次性写完整个功能模块，我们还没达到那个水平，但大概能一次性写完整个文件。那就是当时模型的能力水位。

所以 Claude Code 的理念就是：既然我们认为模型大概率能做到这一点，那如果我们拆除所有多余的脚手架，只给模型提供最极简的控制框架，让它能一次性编写整个文件并构建完整的功能模块呢？事实证明了这一点。这就是当时的“产品势能落差”。模型明明有能力做到，而周围的一切却都在拖后腿。

我认为时至今日，面对现代模型，依然存在巨大的“产品势能落差”，我甚至不敢断言初创公司能完全捕获这些机会。虽然已经有人在思考这些问题，但在激发模型展现出那些令人惊叹、有趣且极具商业价值的行为方面，仍然蕴含着海量的机遇。

### 给 Claude 布置更难的挑战

**主持人：** 我认为这对在座的各位来说是一个极具启发性的洞察。基本上，如果你们能弄清楚如何为模型“解除束缚”，你们任何人都能打造出下一个 Claude Code，因为这本质上就是 Claude Code 的诞生故事。你们为 Sonnet 3.5 解除了束缚，因为之前的所有产品迭代都把模型死死限制在 IDE（集成开发环境）中，显得非常僵化。而 Claude Code 是最早赋予模型完整终端访问权限的产品之一。是的，这进而孕育出了一款不断进化的神奇产品。那么让我们来谈谈，未来的创业者应该如何在“为 Claude 解除束缚”以及弥补“产品势能落差”方面进行思考？具体有哪些领域值得关注？

举个例子，我们有一个 Claude 桌面应用，它是用 Electron 构建的。我们优化了它的运行速度，所以现在体验非常棒。六个月前，它还比较卡顿，也不太可靠。现在它非常流畅，是团队大多数人都在使用的工具。不过，作为一个实验，我想看看如果把它做成原生应用(Native App)，体验会是怎样的。

接着我说：“好，现在我希望你用 Swift 重写这个 Electron 应用。我要你在 Mac 虚拟机中运行 Electron 应用，截取屏幕截图，然后逐像素将其与 Swift 版本进行对比。”

“在完成之前不要停下来。”

### 运行数千个AI智能体

**主持人：** 顺着这个话题，让我们深入探讨一下你两周前启动且至今仍在运行的那个任务。它衍生出了多少个智能体？

**鲍里斯：** 我不确定。我可以去问问 Claude，稍后回复你。我猜有数千个，甚至数万个。

**主持人：** 在座的各位中，有没有人用过能衍生出一千多个智能体的提示词？没有吗？我认为这是另一个秘诀：最优秀的 Claude 用户能够启动真正带来巨大杠杆效应的任务，比如衍生出数千个智能体。

**鲍里斯：** 是的。

**主持人：** 具体怎么做呢？

**鲍里斯：** 有几种不同的方法。最简单的是使用动态工作流(Dynamic Workflows)。这是 Claude Code 中一个相当新的功能。你只需要对它说“使用工作流”，就这么简单。然后 Claude 就会触发动态工作流。

![图片](https://mmbiz.qpic.cn/mmbiz_jpg/GjShauwyBbibptsp8ksah74JJb49lQ07ojGRpiaWtpnQWzia2GxyG3PnYE8jk9b5mB3bykMYuDTKmqlCsWssN8vicwuFeQd7OnicR7ePqlR3vqOA/640?wx_fmt=jpeg&from=appmsg&watermark=1#imgIndex=5)

动态工作流的本质是，我们使用了 Bun 运行时。我们将 Bun 作为沙盒，并在其中启动一个虚拟机。然后，我们让 Claude 启动大量智能体并进行编排。它不仅仅运行单个智能体，也不仅仅运行 10 个并行智能体。

具体来说，假设任务是重写代码库，或者对极其复杂的数据进行深度分析，又或者是构建一个需要多个阶段、可能涉及数十个拉取请求(PR)的复杂功能。它会先启动一批智能体进行初步处理。在此基础上，它可能会进入第二步，派出另一组智能体来验证或总结工作成果。接着可能会进入第三阶段，再次分发任务。因此，它实际上是在高效且富有成效地编排多组不同的智能体。

我的专业背景是函数式编程。因此，我们在设计这套机制时，本质上是为智能体构建了一种代数系统。

既有按顺序运行智能体的方法，也有并行运行的方法。并且 Claude 拥有多种工具，能够在沙盒内编排这些智能体，高效地使用 Token 来完成极其复杂的工作。这非常酷，而且目前关于这方面的深入探讨还不多。

这实际上是一种新形式的推理时计算(Test-time Compute)。当我们谈论规模法则(Scaling Laws)，谈论模型如何随时间推移变得更聪明时，从历史上看，这一直是神经网络规模、训练数据量以及投入训练的浮点运算次数(FLOPs)的函数。

![图片](https://mmbiz.qpic.cn/mmbiz_jpg/GjShauwyBbicR8xKvQypFKxwsxolNfV3FkxhsjIhocwgufCibuvKicDx7LZLBG2BfKfDcfcae0Azh2tOtiahbOlhRF52whxJCdunnhNNRxAicZsw/640?wx_fmt=jpeg&from=appmsg&watermark=1#imgIndex=6)

最近，我们又引入了推理时计算。这本质上是研究人员用来描述“模型生成了多少 Token”的一种高级说法。

如今，动态工作流本质上提供了一种编排推理时计算的新方式。它也是一种能够大幅增加执行高难度任务时所使用的推理时计算量的新途径。所以，说了这么多，我想表达的是：这是一种以高效且富有成效的方式启动数千个智能体的方法。

第二种方法是使用循环(Loops)和例程(Routines)。循环本质上是为 Claude 在本地运行的定时任务(Cron Job)。例程也是同样的东西，但它在云端运行，所以你可以合上笔记本电脑。这两者略有不同：动态工作流是将一个大任务拆分成多个小块；而循环和例程则是执行重复性任务，它们不共享上下文，但可能共享内存。你需要一遍又一遍地执行它，可以设定为每小时、每五分钟或每天执行一次。

因此，我们开始尝试的一件事，是让 Claude 自己维护自己。我们的做法是建立一个 Slack 频道，让 Claude 启动一系列不同的例程来维护它自己的代码库。实际上，我们在命令行界面(CLI)、iOS 应用、Android 应用和桌面端应用上都采用了这种做法。

例如，其中一个例程是“清理死代码”。这只是一个单句提示词。Claude 每天都会运行这个例程。它会利用静态和动态分析，在所有代码库中查找死代码。我们并没有在提示词中具体要求它这么做，它自己就摸索出来了。然后，它每天都会提交拉取请求来删除这些死代码。

![图片](https://mmbiz.qpic.cn/sz_mmbiz_jpg/GjShauwyBb82tSrwOPib7alXM7MRUh3eRgxmjcnGAibwmjEE9hhE6UjuFKercQicjODlVAJNzQeZ6C8lTBXmLw65pP96jFdewuWz5Bd3d6g5Pg/640?wx_fmt=jpeg&from=appmsg&watermark=1#imgIndex=7)

另一个例子是“发布应当全量的实验”。也就是说，当实验已经 100% 全量推送后，它会从代码库中删除相关的实验代码并直接发布。还有一个例程是为代码库中缺乏测试覆盖的区域编写测试。还有一个是删除多余的测试，因为它们可能是早期模型或人类在某个时候添加的无用测试。我非常喜欢其中一个例程，我忘了具体叫什么了，好像叫“抽象警察(Abstraction Police)”。

它的理念是：在庞大的代码库中，通常会出现多次相似的抽象(Abstraction)。如果你眯起眼睛仔细端详，它们实际上可能本该是同一个抽象。但随着时间的推移，出于种种原因，你在代码库的不同部分以多种方式重新构建了它。

所以，Claude 每天会在我们所有的代码库中巡视。它找出这些几乎重复的抽象并将它们统一起来。现在，我们每天大概运行 20 到 30 个这样的例程，覆盖所有代码库。虽然还没达到尽善尽美的状态，但我们正通过这种方式，走在全面实现应用维护自动化的道路上。

这同样意味着每天有数百个、有时甚至数千个智能体在运行。它完成了数十乃至数百名工程师的工作量，而这在以前需要耗费大量人力才能完成。这意味着工程师们可以专注于他们真正想做的事情：发布新产品、与用户交流，以及做那些真正有趣的工作。
