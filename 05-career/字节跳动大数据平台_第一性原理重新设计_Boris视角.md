## 一、字节跳动的核心业务问题

在选任何技术之前，先把业务问题说清楚。字节跳动的数据问题，本质上是**四个核心矛盾**：

### 矛盾一：推荐系统的"饥饿"与延迟的"天花板"

抖音的推荐系统是天底下最"饥饿"的数据消费者。

**数据需求：**
- 用户每刷一个视频，产生一次曝光事件。抖音 DAU ~8亿，人均日使用时长 ~120分钟，按每15秒一个视频计算，**日均事件量约 4-6 万亿条**
- 推荐模型需要这些事件在**秒级**内反馈到特征工程管道——你看了一个视频 5 秒划走 vs 看完 60 秒，这信号完全不同，必须立即反映到下一次请求中
- 同时，推荐模型每天需要**千亿级参数**的训练数据，这是 T+1 离线批量产出的

**矛盾本质：** 同一条数据，既要秒级消费（在线特征），又要天级消费（模型训练），还要支持小时级消费（实时指标监控）。**这是三套 latency SLA，不能混为一谈。**

### 矛盾二：广告系统的"精确性"要求

巨量引擎（字节广告平台）处理的是钱。数据错误 = 钱算错。

**数据需求：**
- 广告曝光、点击、转化的每一条数据必须 **Exactly-Once**，不能丢、不能重
- 广告计费需要**秒级实时**，广告主 dashboard 需要**分钟级**，广告主报表需要**T+1 的可审计精确口径**
- 反作弊检测需要**毫秒级**决策（在广告展示之前就要判断流量质量）
- 归因窗口可能是 1 天、7 天、30 天——意味着需要长时间窗口的多流 Join

**矛盾本质：** 实时计费 + 离线审计必须口径一致。实时链路和离线链路的计算结果差异超过 0.1%，广告主就会来质疑。**实时和离线的"口径对齐"不是锦上添花，是生存问题。**

### 矛盾三：多业务线的"烟囱"与"统一"的张力

字节不是只有抖音。飞书、剪映、番茄小说、懂车帝、朝夕光年……每个业务的数据形态完全不同：

| 业务 | 数据特征 | 核心需求 |
|------|----------|----------|
| **抖音** | 事件流为主，超高吞吐 | 秒级特征 + T+1训练 |
| **飞书** | 文档/消息，结构化+非结构化 | 搜索、协同、知识图谱 |
| **剪映** | 模板/素材使用数据 | AIGC能力+用户行为 |
| **番茄小说** | 阅读行为、章节互动 | 推荐+内容理解 |
| **电商（抖音商城）** | 交易数据，强一致性 | GMV、供应链、物流 |

**矛盾本质：** 全部统一到一个数据平台 → 抖音的 scale 会压垮飞书的需求。各自建烟囱 → 数据打不通，跨业务分析几乎不可能。**你需要的不是"一个平台统治一切"，而是"一套可组合的数据基础设施"——每个业务可以按需组装。**

### 矛盾四：成本与速度的永恒博弈

字节跳动每天产生的数据量级：
- **事件日志：** 日均 ~500TB-1PB 原始日志（压缩后）
- **存储总量：** EB 级别
- **计算资源：** 数十万 CPU Core 持续运行

在这个量级下：
- 一个"全量扫一次"的操作成本可能是几十万元
- 一个"实时聚合"如果设计不当，Flink 状态可能膨胀到 TB 级
- 存储分层（热/温/冷）不是优化，是必需品——热的成本是冷的 10-50 倍

**矛盾本质：** 你不能什么都实时。你必须精确地判断：**哪些数据值得存、值得算、值得实时算。**

## 二、第一性原理分析

把"大数据平台"这个模糊概念拆解到最基础的物理和经济约束。

### 2.1 数据的本质

数据只有两种形态：

1. **事件（Event）：** 在某个时间点发生了一件事。"用户在 t 时刻看了视频 v"、"广告在 t 时刻被点击"。事件是不可变的、只增不减的、天然有序的（按时间）。

2. **实体状态（Entity State）：** 某个实体在某个时刻的属性。"用户 u 的粉丝数是 1200"、"广告计划 p 的预算还剩 3.5 万"。状态是可变的、需要版本管理的。

**推论：** 所有数据基础设施本质上只做三件事——**摄取事件流 → 更新实体状态 → 查询状态**。你的架构如果偏离了这三件事，就是在增加不必要的复杂度。

### 2.2 计算的本质

在大数据场景下，计算只有三种模式：

1. **聚合（Aggregation）：** COUNT、SUM、AVG、HyperLogLog。把大量事件压缩成少量指标。这是最常见、最需要优化的计算。

2. **关联（Join）：** 把两个数据集按某个 key 关联起来。流-流 Join、流-维表 Join、批-批 Join。这是最贵、最容易出问题的计算。

3. **转换（Transform）：** 格式转换、清洗、特征工程。一条进一条出，或一条进多条出。

**推论：** 80% 的"大数据计算"本质上是某种形式的聚合。如果你能极致优化聚合路径，大部分业务需求就能在秒级/分钟级满足。**不要用复杂的 Lambda 架构来处理一个本质上是聚合的问题。**

### 2.3 存储的本质

存储 = 时间 × 空间 × 成本的权衡，三个维度你只能优化两个。

| 如果优化 | 代价 |
|----------|------|
| 查询快 + 成本低 | 只能存少量数据、短时间范围 |
| 查询快 + 存得多 | 成本高（SSD、内存、冗余） |
| 存得多 + 成本低 | 查询慢（冷存储、对象存储） |

**推论：** 必须做分层存储。热的（最近7天，高频访问）用 ClickHouse/Doris 这种 OLAP 引擎；温的（7-90天）用数据湖 Iceberg/Paimon + Presto/Trino 查询；冷的（90天+）用对象存储压缩归档。**不分层 = 浪费 80% 的存储成本。**

### 2.4 物理约束

在字节这个量级下，有一些硬性物理约束不能被工程优化打破：

- **网络带宽：** 跨机房的数据传输是瓶颈。数据必须在产生的地方就近处理（Edge Computing / 就近写入）
- **内存墙：** Flink 状态如果超过单机内存，就必须上 RocksDB + SSD，延迟会增加 10-100 倍
- **一致性 vs 可用性：** 跨机房（Region）的数据一致性不可能同时满足低延迟。必须接受最终一致性
- **热数据倾斜：** 无论怎么分区，头部用户/头部视频的数据量总是尾部 1% 的 1000 倍以上。这是幂律分布决定的，无法通过"均匀分区"解决

**推论：** 在架构设计阶段就承认这些约束，比上线后"打补丁"强一万倍。

## 三、技术路线设计——每个选择的推演

### 3.1 数据摄入层

**选择：** 应用端 SDK（自研）→ 边缘日志服务（Edge Log Service）→ Kafka

**为什么不用别的方式？**

| 方案 | 为什么不选 |
|------|-----------|
| 直接写 Kafka | 客户端网络不稳定 + Kafka 不适合公网暴露。需要中间缓冲 |
| Flume | 太重了。Java agent 内存占用大，配置复杂。字节的场景不需要它的"丰富插件" |
| Logstash | 性能差 Ruby 运行时 |
| **自研轻量 SDK + Edge 服务** | ✅ 客户端 SDK 做本地缓冲 + 批量压缩上传 → Edge 服务聚合 → Kafka。这是唯一能在百万 QPS 公网场景下稳定运行的方案 |

**具体设计：**
```
[App SDK] → 本地SQLite缓冲 → gzip批量上传(每5s或满1000条)
    → [Edge Log Service] → 协议转换 + 字段校验 + 分区路由
    → [Kafka: raw_events topic, partition by user_id%N]
```

**关键决策：** 在 Edge 层做第一道数据质量校验（字段类型、必填字段、时间戳合理性），脏数据直接拒绝并告警，避免脏数据进入 Kafka 污染整个链路。

### 3.2 消息队列层

**选择：** Kafka（主） + 特定场景考虑自研

**为什么 Kafka 不是 Pulsar？**

| 维度 | Kafka | Pulsar | 选择理由 |
|------|-------|--------|----------|
| 生态 | 绝对领先 | 追赶中 | Flink/Spark 对 Kafka 的支持是最成熟的 |
| 运维成本 | 高但可控 | BookKeeper + Broker 两层架构，运维复杂度翻倍 | Kafka 虽然有痛点（Rebalance、分区迁移），但团队已经积累了深厚经验 |
| 性能 | 百万 QPS 单机 | 理论上更好但实际差距不大 | 字节的量级下，Kafka 的零拷贝 + PageCache 已经够用 |
| 多租户 | 弱 | 强 | 字节不是多租户场景——是同一个公司的不同业务线，不需要 Pulsar 级别的隔离 |
| 分层存储 | Kafka 3.0+ 支持 | 原生支持 | Kafka Tiered Storage 已经够用 |

**但是——Kafka 最痛的点需要自研补丁：**

1. **热分区问题：** 头部用户的分区流量是尾部的 1000 倍 → 自研 **Partition Load Balancer**，自动检测热点分区并拆分
2. **Consumer Group Rebalance 风暴：** Flink 作业扩缩容时触发 Rebalance → 自研 **Sticky Assignor** + 预分区策略，将 Rebalance 时间从分钟降到秒
3. **跨 Region 复制：** Kafka MirrorMaker 太慢 → 自研 **Async Cross-DC Replicator**，秒级跨机房同步

### 3.3 实时计算层

**选择：** Apache Flink（核心） + RisingWave（轻量场景）

**为什么 Flink？**

Flink 是大规模实时计算唯一经过验证的选择。Spark Streaming 的 micro-batch 模型无法满足秒级延迟，而字节的推荐特征需要在 **<500ms** 内完成事件→特征的计算。

**Flink 在字节的关键用法：**

| 场景 | Flink 用法 | SLA |
|------|-----------|-----|
| **推荐在线特征** | Flink SQL + DataStream，消费 Kafka → 窗口聚合 → Redis/HBase | P99 < 500ms |
| **广告实时计费** | Flink + Exactly-Once Checkpoint → MySQL/账单系统 | Exactly-Once |
| **实时数仓 DWD/DWS** | Flink CDC + Flink SQL → Kafka/Paimon | P99 < 5s |
| **实时大屏/监控** | Flink → ClickHouse/StarRocks | P99 < 10s |
| **反作弊** | Flink CEP（复杂事件处理），毫秒级规则匹配 | P99 < 50ms |

**为什么增加 RisingWave？**

Flink 太重了。一个简单的"实时去重 + 聚合"需求，用 Flink 需要写 Java/Scala 代码、打 Jar 包、配置 Checkpoint、管理状态后端。RisingWave 用 SQL 就能搞定：

```sql
-- 用 RisingWave 一句话搞定实时 UV
CREATE MATERIALIZED VIEW realtime_video_uv AS
SELECT video_id, COUNT(DISTINCT user_id) as uv, window_end
FROM video_play_events
WATERMARK play_time AS play_time - INTERVAL '5' SECOND
GROUP BY video_id, TUMBLE(play_time, INTERVAL '5' MINUTE);
```

**决策：**
- **核心实时链路：Flink**（稳定性 + 生态 + 团队经验）
- **轻量实时分析：RisingWave**（降低开发门槛，让数据分析师也能写实时SQL）
- **不选 Spark Streaming**——延迟太长，micro-batch 模型不能接受

### 3.4 离线计算层

**选择：** Spark（主力）+ Trino（交互式查询）

**关键决策：要不要统一批和流？**

**不统一。** 虽然 Flink 支持批处理，Spark 支持流处理，但它们各自在自己的领域有不可替代的优势：

| 场景 | 为什么选 Spark（批）而不是 Flink（批） | 为什么选 Flink（流）而不是 Spark（流） |
|------|--------------------------------------|--------------------------------------|
| **模型训练数据产出** | TB 级 Join 和聚合，Spark 的 Adaptive Query Execution（AQE）已经非常成熟 | — |
| **推荐特征** | — | 秒级延迟，Spark micro-batch 做不到 |
| **广告计费** | — | Exactly-Once 语义，Spark Streaming 的保证更弱 |
| **日报/月报** | 复杂的多表 Join，Flink SQL 优化器还不够强 | — |

**具体设计：**

- **Spark 3.5+**：利用 AQE + Dynamic Partition Pruning + Bloom Filter Join。对于广告训练数据的超大表 Join（百亿行 × 千万行），自动选择 Broadcast Hash Join vs Sort Merge Join
- **Trino**：作为 Ad-Hoc 查询引擎，数据分析师用 Trino 直接查 Hive/Paimon 表（统一 SQL 入口）
- **调度：** DolphinScheduler（DAG 编排 + 失败重试 + SLA 监控）

### 3.5 存储层——最关键的决策

这里我需要分层说清楚。

#### 3.5.1 OLAP：ClickHouse vs StarRocks vs Doris

**选择：ClickHouse（核心） + StarRocks（补充）**

| 场景 | 选择 | 理由 |
|------|------|------|
| **实时大屏/监控** | ClickHouse | 单表查询性能无敌。字节的场景主要是大宽表聚合，ClickHouse 的列存 + 向量化执行是天然优势 |
| **多表 Join 分析** | StarRocks | ClickHouse 的多表 Join 比较弱。广告分析经常需要 Join 广告计划表、客户表、创意表，StarRocks 的 CBO 优化器更好 |
| **用户画像标签查询** | ClickHouse + Bitmap | 用户 ID 做 Bitmap 索引，亿级用户的标签交并差在毫秒级完成 |

#### 3.5.2 KV 存储：HBase vs Redis vs 自研

**分层使用：**

| 存储 | 用途 | 数据量 | SLA |
|------|------|--------|-----|
| **Redis Cluster** | 推荐在线特征（最新版）、广告频控 | TB 级 | P99 < 1ms |
| **HBase** | 用户画像全量标签、历史特征 | PB 级 | P99 < 10ms |
| **字节自研 ByteKV**（如果存在） | 替代 HBase，更好的 SSD 优化 | PB 级 | P99 < 5ms |

#### 3.5.3 数据湖：Iceberg vs Hudi vs Paimon

**选择：Apache Paimon（主） + Apache Iceberg（已有资产兼容）**

**为什么 Paimon 而不是 Hudi 或 Iceberg？**

| 维度 | Iceberg | Hudi | Paimon | 选择 |
|------|---------|------|--------|------|
| **流式写入** | 中等（需要 Flink Iceberg Connector） | 强（Copy-on-Write/Merge-on-Read） | **最强**（原生 Flink 集成，LSM 树引擎） | Paimon 胜 |
| **主键更新** | 较弱（Merge Into） | 强（Record Key + PreCombine） | **强**（LSM 树天然支持 Upsert） | Paimon = Hudi |
| **Flink 生态** | 一般 | 一般 | **最好**（Paimon 就是为 Flink 设计的） | Paimon 胜 |
| **查询性能** | 好（成熟生态 Presto/Trino/Spark） | 一般 | 好（原生支持 Trino/Spark/StarRocks） | Iceberg 略胜（生态更成熟） |
| **社区活跃度** | 最高 | 中 | 快速增长（阿里+字节推动） | Iceberg 胜 |

**决策：**
- 新业务全部用 **Paimon**（流批一体、主键更新、Flink 原生）
- 已有 Iceberg 表继续保留，逐步迁移
- 不用 Hudi——工程复杂度高，小文件问题比 Paimon 严重

**Paimon 在字节的核心场景：**

```
ODS（原始日志）→ Kafka
    ↓ Flink 清洗
DWD（明细宽表）→ Paimon（主键 Upsert，CDC 同步）
    ↓ Flink/Spark 聚合
DWS（汇总表）→ Paimon + ClickHouse（Paimon 存全量，ClickHouse 存热数据）
    ↓ Trino 查询
ADS（应用层）→ ClickHouse/StarRocks + Redis（缓存热查询结果）
```

### 3.6 搜索：Elasticsearch vs Solr vs 自研

**选择：Elasticsearch（已有）→ 长期演进到自研**

ES 在字节最大的问题是**写入吞吐**和**内存开销**。在用户画像标签搜索、日志全文检索等场景，ES 倒排索引的内存膨胀非常严重。长期来看，字节量级的搜索场景需要更轻量的自研方案（参考 Snowflake 的 Search Optimization Service 的设计思路），但短期内 ES 是最务实的选择。

### 3.7 数仓建模：维度建模还适用吗？

**答案：适用，但要升级。**

Kimball 的维度建模（星型/雪花模型）在 1996 年提出，但它解决的核心问题——**"如何让业务用户理解数据"**——在今天仍然成立。

但需要三个升级：

1. **从星型到宽表：** 在 OLAP 引擎（ClickHouse）上，不要建星型模型——直接建大宽表。列存的压缩率 + 向量化执行让宽表查询极快，而且业务用户更容易理解。星型模型只保留在数据湖层（Paimon/Iceberg），用于灵活 Ad-Hoc 分析。

2. **从 T+1 分层到实时分层：**
   ```
   ODS（原始）→ 实时（Kafka → Flink → Paimon，秒级）
              → 离线（Kafka → HDFS → Spark → Paimon，小时级）
   DWD（明细）→ 实时 + 离线统一（Paimon 存储，Flink/Spark 均可读写）
   DWS（汇总）→ 实时预聚合（Flink → ClickHouse） + 离线全量（Spark → Paimon）
   ADS（应用）→ 查询时 Join（StarRocks）或预计算 API（Redis + SpringBoot）
   ```

3. **从"人建模型"到"AI 辅助建模"：**
   - 用 LLM 自动生成维度建模建议（根据业务查询 pattern 推荐哪些维度放到一张宽表）
   - 用 AI 做数据血缘自动发现（解析 SQL 日志，自动构建字段级血缘）
   - 用 AI 做异常检测（自动监控指标波动，告警 + 初步根因分析）

### 3.8 调度与编排

**选择：DolphinScheduler（主） + 自研实时任务管理平台**

| 组件 | 用途 |
|------|------|
| **DolphinScheduler** | 离线任务 DAG 编排（Spark/Hive/Shell/Python），SLA 监控，失败告警 |
| **自研 Flink 管理平台** | Flink 作业的发布、扩缩容、Checkpoint 管理、日志收集 |
| **自研数据质量平台** | DQC（Data Quality Center），字段级质量监控、分区级校验 |

### 3.9 AI + 数据平台

这是最重要的差异化部分。在 2026 年，不把 AI 融入数据平台就是在浪费机会。

**三个层次的 AI 融入：**

| 层次 | 场景 | 方案 |
|------|------|------|
| **L1: AI 辅助数据开发** | SQL 生成、ETL 代码生成、数据校验规则生成 | NL2SQL（Claude/GPT）+ 代码补全（Copilot/Codex） |
| **L2: AI 驱动数据治理** | 自动发现数据质量问题、自动推荐优化方案 | LLM 分析查询日志 → 识别慢查询 → 自动生成优化建议 |
| **L3: AI 自治数据平台** | 自动扩缩容、自动数据生命周期管理、自动故障恢复 | Agent 架构（多智能体协作），持续监控 + 自动决策 |

**在 Phase 1 就引入 L1 的 NL2SQL 能力——让数据分析师和 PM 可以直接用自然语言查数据。** 这是"60分就发布"的典型应用：不需要等整个平台建好，先在数据查询这个最高频的场景切入，马上产生价值。

## 五、分阶段交付计划

### Phase 1：最小可用数据平台（0-3个月）

**核心问题：** 先把"数据能看、能查、能出报表"这件事搞定。这是基础设施的 60 分版本。

**技术栈（最小集）：**
```
App SDK → Kafka → Flink(基础清洗) → HDFS/Hive(ODS+DWD)
                                      ↓
                                  Spark(天级聚合)
                                      ↓
                              ClickHouse(DWS热数据) + Paimon(DWS全量)
                                      ↓
                                  Trino(查询入口)
                                      ↓
                                  Superset(可视化)
```

**不做的事：**
- 不做实时数仓（Phase 2 再做）
- 不做复杂的事件处理（只用 Flink 做基础 ETL）
- 不做自研组件（全部用开源 + 最小配置）
- 不做 AI 融入（Phase 1 结束时再启动 NL2SQL POC）

**交付物：**
1. 数据从 App 到可查询，端到端延迟 < 1 小时（T+1 是基本要求，1小时是 Phase 1 目标）
2. 核心 10 张业务宽表（用户行为、视频消费、广告曝光、点击…）
3. 日报/周报自动产出（DolphinScheduler 调度）
4. 数据分析师可以通过 Trino 做 Ad-Hoc 查询

**校验标准：**
- [ ] 数据从产生到可查询延迟 < 1 小时（P99）
- [ ] 核心宽表数据质量：空值率 < 1%，重复率 < 0.01%
- [ ] 日报准时产出率 > 99%（6个月内）
- [ ] 分析师 Ad-Hoc 查询 P90 < 30 秒
- [ ] 系统可用性 > 99.5%

### Phase 2：规模化与实时化（3-9个月）

**核心问题：** 把实时能力加进来，把规模扩到多业务线。

**新增技术栈：**
```
Phase 1 基础
    +
Flink CDC (MySQL Binlog 实时入湖)
    +
Flink 实时聚合 (DWD → DWS, 秒级)
    +
ClickHouse 实时大屏 (P99 < 5s)
    +
Paimon 流式写入 + 主键更新
    +
RisingWave (轻量实时分析)
    +
多业务线数据隔离 (Kafka Quota + Paimon Namespace)
```

**关键架构变更：**
1. Kafka → Flink → Paimon 实时链路（替代 Phase 1 的 Kafka → HDFS 小时级链路）
2. DWD 明细层实现批流一体（Flink 实时写 Paimon + Spark 离线补数据，同一张表）
3. 广告计费链路切换到 Exactly-Once 模式
4. 多业务线通过 Namespace 隔离（Paimon 的 catalog 机制）

**交付物：**
1. 实时数仓上线，核心指标延迟 < 10 秒
2. 广告实时计费链路 SLA 99.99%
3. 推荐在线特征延迟 < 500ms
4. 支持 5+ 业务线接入
5. 数据血缘自动追踪（元数据平台）

**校验标准：**
- [ ] 实时大屏数据延迟 P99 < 5s
- [ ] 广告计费 Exactly-Once，零丢零重
- [ ] 推荐特征延迟 P99 < 500ms
- [ ] 新业务线接入数据平台 < 1 周（从申请到第一张表）
- [ ] 系统可用性 > 99.9%
- [ ] 存储成本 < ¥0.05/GB/月（热数据），< ¥0.005/GB/月（冷数据）

### Phase 3：智能化与自治（9-18个月）

**核心问题：** AI 融入数据平台的每个环节，从"人驱动"变成"AI 驱动"。

**新增能力：**

| 能力 | 方案 | 预期效果 |
|------|------|----------|
| **NL2SQL 全公司开放** | Claude/GPT + Schema 检索，任何人用自然语言查数据 | 数据查询量提升 10x，分析师工作量降低 50% |
| **AI 自动数据治理** | LLM 分析查询日志 → 识别无用表 → 自动归档建议 | 存储成本降低 30% |
| **智能异常检测** | 时序异常检测模型 + LLM 根因分析 | 故障发现从"人肉看监控"到"Agent 自动告警" |
| **自动 SQL 优化** | LLM 分析慢查询 → 自动改写 + 自动建议建索引 | 慢查询减少 60% |
| **AI 数据建模助手** | 基于查询 Pattern 自动推荐宽表设计 | 数据建模效率提升 3x |
| **自治运维** | Agent 自动处理常见故障（扩容、重启、数据回刷） | MTTR 降低 80% |

**校验标准：**
- [ ] NL2SQL 查询量 / 总查询量 > 30%
- [ ] AI 自动发现的数据质量问题 > 60%（相比人工规则）
- [ ] 存储成本相比 Phase 2 降低 30%（通过 AI 驱动的生命周期管理）
- [ ] 故障 MTTR < 5 分钟（P99）
- [ ] 新业务接入数据平台 < 1 天（从申请到第一张表）
- [ ] 系统可用性 > 99.99%
- [ ] 数据平台人效：1 个数据工程师支撑 5 个业务线的数据需求

## 六、校验标准

### 整体指标体系

| 指标类别 | 指标 | Phase 1 | Phase 2 | Phase 3 | 测量方式 |
|----------|------|---------|---------|---------|----------|
| **延迟** | 端到端数据可用延迟 | < 1h (P99) | < 10s (实时) | < 5s (实时) | 监控埋点 |
| **延迟** | 推荐特征延迟 | — | < 500ms | < 200ms | Flink 指标 |
| **质量** | 数据完整性（丢表率） | < 0.1% | < 0.01% | < 0.001% | 对账任务 |
| **质量** | 数据重复率 | < 0.01% | 0% (Exactly-Once) | 0% | 对账任务 |
| **可用性** | 平台整体可用性 | 99.5% | 99.9% | 99.99% | 监控系统 |
| **成本** | 每 TB 数据处理成本 | ¥50 | ¥30 | ¥20 | 财务+资源系统 |
| **成本** | 存储成本 (热/冷) | ¥0.1/¥0.01 | ¥0.05/¥0.005 | ¥0.03/¥0.003 | 存储审计 |
| **效率** | 新需求响应时间 | 7天 | 3天 | 1天 | 工单系统 |
| **效率** | 工程师人效比 | 1:2 | 1:3 | 1:5 | OKR 跟踪 |
| **满意度** | 业务方满意度评分 | 3.5/5 | 4.0/5 | 4.5/5 | 季度 NPS |

### 每个阶段的"不妥协"标准

这些是 **Must Have**，达不到就不能进入下一阶段：

**Phase 1 不妥协标准：**
- 端到端延迟 P99 < 1h（这个做不到，后面的实时化就是空中楼阁）
- 无丢表风险（单机故障能在 30 分钟内 Failover）

**Phase 2 不妥协标准：**
- 广告计费 Exactly-Once（涉及钱，这是底线）
- 实时链路和离线链路口径误差 < 0.1%（否则广告主不信任）

**Phase 3 不妥协标准：**
- AI 生成的 SQL 在安全上零事故（不允许 DELETE/DROP/ALTER 越过校验层）
- 自动运维操作必须有回滚能力（Agent 不能做不可逆操作）

## 七、附录：关键决策记录

> 这部分记录设计过程中做过的重要 Trade-Off 决策，供后续团队质疑和迭代。

| # | 决策 | 备选方案 | 选择理由 | 代价/风险 |
|---|------|----------|----------|-----------|
| 1 | Kafka 而非 Pulsar | Apache Pulsar | 生态成熟度 + 团队经验 | 多租户隔离弱，需要自研补丁 |
| 2 | Paimon 而非 Iceberg（新业务） | Apache Iceberg | Flink 原生集成 + LSM 主键更新 | 社区规模不如 Iceberg |
| 3 | 不统一批流 | Flink 做全量批处理 | Spark 批处理优化器更成熟 | 两套引擎，运维复杂度高 |
| 4 | ClickHouse + StarRocks 双 OLAP | 只用一个 | ClickHouse 单表无敌，StarRocks 多表 Join 更强 | 数据在两个引擎间可能有延迟 |
| 5 | DolphinScheduler 而非 Airflow | Apache Airflow | Airflow 太重 + Python 依赖复杂 | DolphinScheduler 社区较小 |
| 6 | 数仓保留分层但增加宽表 | Data Mesh / 全宽表 | 宽表查询快，分层保留灵活 | 宽表冗余存储成本高 |
| 7 | Phase 1 不引入实时数仓 | 一上来就做实时 | 先用最小系统跑通，避免过早优化 | Phase 1 到 2 有返工成本 |

> **设计总结：**
>
> 这份设计的核心思想不是"用什么最先进的技术"，而是 **"用什么技术能以最小的成本和复杂度，在最短时间内，解决字节跳动最核心的数据业务问题"**。
>
> 每一个阶段都遵循"60分就发布"的原则——Phase 1 不追求实时，Phase 2 不追求 AI 智能化，Phase 3 才引入 AI。每个阶段的交付物都有清晰的、可量化的校验标准。
>
> 如果你质疑某个决策——欢迎。这份文档存在的意义就是被质疑和迭代。但质疑时请带上数据和替代方案，而不是"我觉得应该用 X"。
